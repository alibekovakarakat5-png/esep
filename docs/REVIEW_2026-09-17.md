# Пересмотр Esep перед бухгалтерским пилотом

## Исправления прежних выводов

- Аудит не был полным: скриншоты и выборочные исходники не заменяют прохождение всех страниц под двумя аккаунтами.
- «СО 3,5% → 5%» неверно как изменение 2025→2026. Пять процентов действует с 2025. В `diagnosis_service.dart` старый год задан неправильно, значит дельта может завышаться. Источник: https://www.gov.kz/memleket/entities/kyzylorda-kzo/press/article/details/222143
- «СН для ТОО упрощён» на скрине означает упрощение расчёта, а не буквально название режима. Однако код действительно начисляет СН всем ТОО с работниками, не проверяя режим, поэтому ошибка применимости подтверждена. Источник: https://www.gov.kz/memleket/entities/kgd-kostanay/press/news/details/1141317?lang=ru
- Отсутствие GROQ_API_KEY — подтверждённая ветка 503 в коде, но не подтверждённое состояние Railway. До логов/окружения причина прод-сбоя остаётся предположением.
- OCR присутствует в мобильном коде; в вебе вместо него заглушка «Доступно только в мобильном приложении». Его нельзя называть почти готовым веб-импортом.
- Две кнопки сохранения сами по себе не создают дубль. Существенно отсутствие блокировки повторного запроса и новой UUID при каждом вызове; прод-сценарий конкретного дубля не воспроизведён.

## Сильные стороны — с границами доказанного

1. Есть самостоятельное Node-ядро налоговых расчётов, версия ставок и общие тестовые данные для сравнения с Dart. 54 выбранных теста сейчас проходят. Это хорошая основа, но диагностика и бухгалтерский календарь используют отдельную логику и уже разошлись.
2. Реализованы чтение банковских файлов, PDF/XML документов, XLSX-разбор ЭСФ и алгоритм поиска расхождений. Есть что проверить на реальных обезличенных примерах, не начиная всё заново.
3. Портфель бухгалтера сохраняется на сервере; присутствуют проверка владельца и транзакция upsert клиентов. Это полезнее локального списка, но модель организации пока не связывает весь документооборот.
4. В CI есть обязательные тесты расчётного ядра, моделей, парсера и генератора ЭСФ. Это подтверждено конфигурацией, не текущим статусом GitHub Actions.
5. Уже собраны лиды и подготовлены материалы интервью. Ближайшая возможность — закрытый пилот с несколькими практиками, а не массовое обещание готовой автоматизации.

## Архитектура, которую предлагаю

Сохранить Flutter + Node + PostgreSQL. Сейчас переписывание платформы не оправдано. Ввести ясные границы: аккаунт бухгалтера → рабочее пространство → обслуживаемая организация → документы/операции/сотрудники/периоды. Во всех запросах проверять владельца и организацию. Контрагент в счёте и компания на обслуживании — разные сущности, их нельзя автоматически считать одной карточкой.

Для каждого импорта: организация, источник, период, идентификатор загрузки, предпросмотр, подтверждение, ошибки строк и ключ повторяемости. Сверка не должна удалять записи по одному лишь имени файла. Для налогов: тип лица + режим + регион + дата действия + источник + версия; интерфейс использует общее ядро или общие проверенные тесты, не самостоятельные формулы на каждом экране.

Счёт — документ. Оплата — отдельное событие, которое может быть частичным, возвращённым или найденным в банковской выписке. Автоматический доход по факту выпуска счёта внедрять нельзя без правил конкретного учёта.

Connect держать отдельной CRM с отдельным доступом. Для приглашений в Esep достаточно связи идентификаторов лида и пилота; налоговые данные клиентов не следует копировать в общую базу лидов.

## Инструменты и модели

По выбранной пользователем схеме сильная модель отвечает за эту архитектуру, налоговые правила, сложные баги, код критических сценариев и ревью. Более лёгкая получает ограниченную задачу: путь, ожидаемое поведение, тест приёмки, запрет расширять объём. Модель автоматически не переключалась.

Добавлен короткий AGENTS.md → PROJECT_STATE.md. Это штатный механизм инструкций: https://learn.chatgpt.com/docs/agent-configuration/agents-md

Установлен Repomix 1.18.0: https://github.com/yamadashy/repomix — только точечная сборка контекста бухгалтерского модуля. Он не предотвращает повторный анализ сам по себе: решения и статусы остаются в Markdown, а после изменения исходников их нужно перепроверять.

Serena проверена как кандидат: https://github.com/oraios/serena — семантическая навигация, в том числе Dart. Не установлена: нет Dart/Flutter в PATH, а польза второго инструмента пока не измерена. Массовая установка похожих memory/MCP-репозиториев не является доказанным способом экономии токенов.

Найден открытый ключ Connect в историческом HANDOFF. Не скопирован в новые файлы, не использован. Нужна ротация и очистка истории при подтверждённой актуальности; это отдельное согласуемое изменение конфигурации.
