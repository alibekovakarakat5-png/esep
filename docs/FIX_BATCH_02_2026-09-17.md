## Сверка: защита и старые данные

- Новый реестр `esf_recon_registry_row` и результаты `esf_recon_result` изолированы по session_id. Старые `esf_invoice` / `esf_recon_match` не удалялись и автоматически не распределялись между компаниями.
- В `esf_recon_session` добавлены `accounting_client_id` и снимок ИИН/БИН `client_bin`. Старая сессия без организации показывается с требованием повторного импорта; API не позволяет использовать её как проверенную организационную сверку.
- Импорт сверяет ИИН/БИН покупателя каждой строки реестра с выбранной компанией. Отсутствующий или чужой идентификатор отклоняется. Нужно проверить реальные обезличенные шаблоны выгрузки перед пилотом.
- Парсер извещения пока не извлекает ИИН/БИН получателя документа. Принадлежность извещения пользователь проверяет по явно показанной компании; автоматическая проверка именно этого файла не заявляется.
- Замена файла и пересчёт результатов выполняются транзакционно. Неудачная запись не уничтожает предыдущий успешный импорт. Успешный повторный импорт сбрасывает устаревшие результаты.
- Один session_id при повторной отправке формы не создаёт дубликат и не допускает смены организации/периода существующей сессии.
- Составные внешние ключи дополнительно запрещают связи результата с другой сессией и компании с чужим аккаунтом.

## Гонорары и миграция

- `accounting_fee_payments`: ключ client_id + month, сумма при первой отметке, статус и время изменения. Повтор PUT не создаёт второй платёж. Изменение текущего тарифа не пересчитывает прошлые суммы.
- Отмена меняет статус, а не удаляет запись месяца. Полный журнал каждого нажатия не реализован.
- Старый boolean сохранён как неизвестный по месяцу и не засчитывается в текущий месяц. UI объясняет это; пользователь явно отмечает нужный месяц. Нельзя придумывать исторический месяц из прежней галочки.
- Миграция добавлена в существующую последовательность старта backend. При будущем запуске нового backend она будет применена автоматически; сначала нужна резервная копия и проверка на staging. В этой работе она выполнялась только в изолированной тестовой БД.

## Календарь: проверенные источники и границы

Проверены официальные публикации:

- https://www.gov.kz/memleket/entities/kgd-almaty/press/news/details/1265649?lang=ru — срок 17.08.2026 для 200.00 за II квартал и 910.00 за I полугодие; платежи августа относятся к июлю.
- https://www.gov.kz/article/33969 — календарь праздников/выходных 2026.
- https://www.gov.kz/article/16887 — календарь и правила переноса.

В коде учитываются дни, а не оставшиеся часы; срок сегодня не пропадает вечером. Для 2026 заложены проверенные праздничные переносы; для других лет появляется оговорка об уточнении календаря. Неактивные клиенты и отменённые режимы ЕСП/патент не генерируют текущие сроки. 700 имеет оговорку о наличии объектов. Применимость всех форм по режимам/налоговым агентам ещё требует отдельной матрицы и проверки бухгалтером; налоговая диагностика не исправлялась этим пакетом.
