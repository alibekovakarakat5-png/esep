# Предложения к изменениям — ожидание согласования

Ни одно из предложений ниже не реализовано. Этот файл нужен, чтобы перед каждой правкой было видно: причина, ожидаемая работа и проверка.

## CP-01. Разделить стартовый путь ИП и ТОО

**Причина:** QA-002, QA-003, QA-015, QA-017. ТОО сейчас видит налог 910, лимит упрощёнки и платежи ИП. Это может привести к неправильному действию пользователя.

**Как изменить:**

- Сохранить существующий дашборд для ИП.
- Для ТОО создать отдельную конфигурацию задач и метрик: заполнить реквизиты компании → импортировать выписку → сверить доходы/расходы → указать статус НДС → сотрудники → расчёт КПН/НДС/соцплатежей.
- Не показывать форму 910, лимит упрощёнки, ЕСП и патент, пока пользователь явно не выбрал совместимый режим.

**Как будет работать:** ТОО сразу понимает следующий шаг и видит только относящиеся к компании обязательства. Если данных недостаточно для расчёта — интерфейс показывает «нужно заполнить», а не сумму налога.

**Как проверить:** новый аккаунт ТОО и аккаунт ИП проходят один и тот же путь; на ТОО нет 910/ЕСП/патента, на ИП сохраняется текущий сценарий.

## CP-02. Сделать тарифы сегментными

**Причина:** QA-004, QA-011. ТОО видит бухгалтерские планы и «дополнительный бизнес».

**Как изменить:** передавать `UserMode` в paywall и отдавать набор карточек по сегменту. До утверждения коммерческой модели не придумывать цены: для ТОО показывать один понятный пилотный план с текущей ценой только после твоего решения; бухгалтеру — тарифы по количеству клиентов.

**Как будет работать:** ТОО покупает доступ к своему кабинету, бухгалтерская фирма — лимит клиентов и функции портфеля. Кнопка оплаты формирует сообщение с правильным тарифом.

**Как проверить:** открыть paywall из ИП, ТОО и бухгалтера; состав карточек, сумма, текст и WhatsApp-заявка совпадают с выбранным режимом.

## CP-03. Исправить обещание «счёт автоматически попадает в 910»

**Причина:** QA-018. Сейчас это неправда по коду.

**Вариант A — быстрый и безопасный:** заменить текст: «После оплаты отметьте поступление в Учёте или импортируйте выписку». Это не меняет финансовые данные.

**Вариант B — продуктовый:** при отметке «Оплачен» показать предпросмотр создания доходной операции. Пользователь выбирает дату и подтверждает. В модели хранится `invoiceId`, чтобы повторная отметка не создала дубль.

**Как будет работать после B:** счёт остаётся документом, а деньги появляются в учёте только после подтверждения факта оплаты. Это безопаснее, чем автоматически считать неоплаченный счёт доходом.

**Как проверить:** создать счёт → отметить оплачен → подтвердить операцию → увидеть одну доходную операцию и пересчёт; повторить статус — дубля нет.

## CP-04. Восстановить Консультанта только с проверяемыми источниками

**Причина:** QA-005, QA-012, QA-013. В коде отсутствие `GROQ_API_KEY` вызывает 503, но конфигурация прод-окружения ещё не проверена; это гипотеза причины. Знания нельзя назвать актуальными без аудита базы.

**Как изменить:**

1. Проверить в Railway наличие корректного ключа и лимитов провайдера, не раскрывая секрет.
2. Добавить health-check провайдера и понятный fallback в UI.
3. Ввести реестр источников: URL, тип, дата публикации, дата проверки, владелец, применимость для 2026.
4. Перед ответом об обязательствах требовать официальную цитату; без неё отвечать «нет проверенного ответа».
5. Добавить еженедельную проверку свежести и ручной выпуск обновления после изменения НК/писем КГД.

**Как будет работать:** Консультант становится помощником по интерфейсу и навигатором по проверенным источникам, а не заменой бухгалтера. Если поставщик или база недоступны, пользователь получает кнопку инструкции/обращения, а не пустой нерабочий чат.

**Как проверить:** 20 эталонных вопросов ИП, ТОО и бухгалтера; каждый налоговый ответ содержит действующий источник, верные сроки и не обещает непроверенное.

## CP-05. Подготовить пилот 1С, не рекламируя «один клик» преждевременно

**Причина:** QA-014. Коннектора нет.

**Как изменить:** реализовать сначала экспорт/импорт для одной согласованной конфигурации 1С либо read-only HTTP-расширение. Детали — в `1C_INTEGRATION_DISCOVERY.md`.

**Как будет работать:** бухгалтер подключает тестовую базу с ограниченными правами или загружает файл, сверяет данные и видит журнал импорта. В 1С на первом этапе ничего не записывается.

**Как проверить:** тестовая база одного бухгалтера; три контрольные цифры совпадают с 1С, повторный импорт не создаёт дубликаты.
