# Первый пакет исправлений: сохранение клиента

2026-09-17. Пользователь разрешил начать исправление шести перечисленных проблем. Реализация локальная; деплой и миграции production не выполнялись. Целевой покупатель — бухфирма. Отдельные бухгалтеры — тестировщики по бартеру. Предыдущие запреты изменения кода в исторических документах для этих шести исправлений заменены этим разрешением.

## Что изменено и почему

1. Форма редактирования использует copyWith текущего клиента, а не новый объект с умолчаниями. Сохраняются сотрудники, чек-лист, оплата и isActive. Берётся последняя загруженная версия, если она есть. Это не решает серверное конкурентное редактирование из нескольких вкладок.
2. ID создаётся один раз на открытие формы. Защита _saving блокирует повторный вызов до перестроения UI; обе кнопки отключены, поля не меняются во время запроса. Повтор после ошибки использует тот же ID для существующего server upsert. Это не уникальность БИН между разными вкладками/новыми формами.
3. Форма закрывается только при подтверждённом успехе. Ошибка оставляет введённые данные и возможность повторить. Формулировка «сохранение не подтверждено» учитывает потерю ответа после успешной записи на сервер.
4. addClient/updateClient публикуют состояние только после успешного запроса. Повторный add того же ID не дублирует локальный список. Проверяется mounted после await.
5. copyWith поддерживает clearNotes, чтобы очистка заметок сохранялась после перехода с конструктора на copyWith.
6. Вынесена переопределяемая граница записи accountingClientWriterProvider для тестов без production.

Изменены: lib/features/accountant/screens/add_accounting_client_screen.dart; lib/core/providers/accounting_provider.dart; lib/core/models/accounting_client.dart.

## Более широкий Esep: уточнение после сайтов и кода

Просмотрены https://business.esepkz.com/ и https://buhfirma.esepkz.com/ в браузере. Business позиционируется как инфраструктура для платформ/агрегаторов: API, проверки, лимиты, фискальные процессы. Buhfirma — рабочая система фирмы: портфель, расчёты, формы, зарплата, интеграции, white-label. Клиентский портал — возможный вспомогательный канал фирмы, не смена текущей ЦА.

Код server/src/routes/platform/index.js и process_payment.js подтверждает существование отдельного Platform API, ключей/разрешений, маршрутов проверок/лимитов/чеков и оркестрации. При этом фискализация зависит от PLATFORM_FISCALIZATION_ENABLED, а реестр самозанятых/льготы обозначены demo_mode. Боевые договоры, интеграции и SLA этим не подтверждены.

Архитектурное направление: общее версионированное налоговое ядро, модель организаций/прав, финансовые документы/события, интеграционные адаптеры, аудируемые фоновые операции. Сверху — разные продукты и контракты: кабинет бухфирмы; API для платформ; в будущем управленческий кабинет ТОО. Общий код НЕ означает общий доступ к данным, общий тариф или одинаковые процессы.

Последующее расширение бухфирмы: роли команды и проверка старшим бухгалтером; массовые операции по портфелю; получение и подготовка первички; контроль сдачи с квитанциями; трудозатраты/рентабельность обслуживания; onboarding/offboarding; затем white-label. Через эти же данные возможен отдельный продукт для директора, но сейчас его не строим. Платформенные массовые выплаты требуют отдельной проверки идемпотентности, параллельности, сверки с внешними провайдерами и восстановления после сбоев.

Коммерческие обещания требуют доказательств: buhfirma — 25 ч/нед и рост портфеля 10→30, данные в РК, формы/ИСНА; business — 99.9%, <100 мс, серверы в РК, договоры КГД/Webkassa, все требования закона. На Business одновременно есть утверждение о покрывающем договоре КГД и отметка «договор в процессе» для реестра — объём готовности нуждается в разъяснении. Это аудит заявлений, не юридический вывод. Сайты не редактировались.

Ближайший фокус: надёжность для бухфирм, не расширение ЦА. Масштабирование должно повторно использовать доказанные модули, а не размножать непроверенные обещания.
